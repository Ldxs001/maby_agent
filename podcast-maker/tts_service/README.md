# 本地 TTS 服务（Qwen3-TTS）

主程序只需要「一句文字 → 一个 wav」。模型的重活（PyTorch、CUDA、几个 GB 权重）
按需安装，**主程序不引入 torch**，双击 `setup.bat` 依旧能起。

**环境由程序建，不由用户建。** 本服务跑在自己的 `.venv` 里（`python -m venv`
建出来的），与主程序的环境互不干扰。理由不是洁癖：这一套装完占 4.8 GB
（torch 轮子下载 2.41 GiB，落到 `site-packages/torch` 占 3.9 GB），外加一串钉死
版本的包，装进主程序环境会把它的依赖一起搅动；而主程序对这件事的全部要求
只是「能用」。建这一步不需要用户动手——配置页选 Qwen3-TTS，点一次
「搭建本地语音环境」即可。

---

## 一、一键安装

两个入口，跑的是同一份实现：

| 入口 | 场景 |
|---|---|
| 配置页 →「语音引擎」选 Qwen3-TTS → 点**「搭建本地语音环境」** | 正常路径。缺什么补什么，进度就在那张卡上 |
| 双击 **`setup.bat`** | 想先在命令行把它装好时用 |

两者都调 `setup_env.py`，它做五件事：

| 步 | 做什么 |
|---|---|
| 1 | 找机器上一个 Python 3.11+（**只用它建环境**，之后服务不跑在它上面；3.11 优先，见下） |
| 2 | `python -m venv tts_service/.venv` 建出本服务自己的环境 |
| 3 | 装依赖：PyTorch（**CUDA 版**，torch 轮子 2.41 GiB、torchaudio 2.0 MiB）+ 代码真正 import 的那几个 |
| 4 | 装两个 TTS 本体包（`--no-deps`，见下面的坑） |
| 5 | 下两个模型权重（Base + CustomVoice，各约 4.3 GB，**可断点续传，重跑不会重下**） |

再跑一次不会重装：环境、依赖、模型三样都齐时它直接收工。中途断了可以重跑，
已装好的包和已下好的权重都留着。

**为什么 3.11 优先。** PyTorch 的 CUDA 轮子在这份镜像上覆盖 cp310–cp314，但周边
那串包（onnxruntime、librosa 等）在新版 Python 上常常还没有轮子。3.11 是覆盖面
最广的一档；找不到就顺着往上找，一个都没有才报错。

权重默认落在 `models/` 下，**两个变体都要**：

| 权重 | 目录 | 谁用 |
|---|---|---|
| `Qwen3-TTS-12Hz-1.7B-Base` | `models/Qwen3-TTS-12Hz-1.7B-Base/` | 常驻服务的那个（`serve.py` 默认吃它） |
| `Qwen3-TTS-12Hz-1.7B-CustomVoice` | `models/Qwen3-TTS-12Hz-1.7B-CustomVoice/` | 只在录参考音频时短暂跑一次（`make_voice.py`） |

两个各约 4.3 GB（`model.safetensors` 分别是 3857413744 / 3833402552 字节）。
**不能只装一个**：Base 没有内置音色、出不了参考音频；CustomVoice 没有说话人编码器、
读不了参考音频。两者也不能同时驻留 —— 8 GB 的卡上放不下，所以分工是「常驻的不管录音、
录音的不常驻」。

**下载源**（全仓唯一写死在 `../tools/sources.py`，`setup_env.py` 从那里读，
`requirements-*.txt` 里各带自己那一条，有测试盯着几处不许走散）：

| 用途 | 源 |
|---|---|
| PyPI 包 | 清华 `https://pypi.tuna.tsinghua.edu.cn/simple/`（备用：阿里云 / 腾讯云 / 中科大） |
| PyTorch CUDA 轮子 | 上海交大 `https://mirror.sjtu.edu.cn/pytorch-wheels/cu126/`（备用：官方 `download.pytorch.org/whl/cu126`） |
| 模型权重 | ModelScope → `hf-mirror.com` → HF 官方，一条断了自动换下一条 |

这几个源都是**实测过的**，不是照抄别人的清单：清华、阿里云、腾讯云、中科大的 PyPI
源均返回 200；`torch-2.9.1+cu126-cp311-cp311-win_amd64.whl` 在交大源上确认存在。
反过来说，清华 / 阿里云 / 北外 / 南大 / CERNET 的 `pytorch-wheels` 路径实测 404 或
不含该轮子，所以**没有写进来** —— 写进去看着丰盛，实际是把用户送去一个死地址。

### 安装路上踩过的四个坑（脚本里已绕开，写下来免得重走）

1. **PyPI 上 Windows 的 `torch` 是 CPU 版。** 装完 `torch.__version__` 会显示 `+cpu`，
   而 CPU 版**永远用不了 GPU**，配置里写什么都不管用。所以脚本改成从 PyTorch 镜像
   装 `torch==2.9.1+cu126`（配套 `torchaudio` 同版本）。装完脚本会自检
   `torch.version.cuda` 是否为真，不是就换官方源再试。
2. **不要加 `--extra-index-url`。** 多一个源，pip 就对**每一个包**向两个源各查一遍；
   在中文网络下会卡到十几分钟连 torch 都没开始下。只认单一镜像。
3. **官方依赖清单里挂着一堆用不到的东西**（gradio 全家桶等）。所以先装代码真正
   import 的那几个，再用 `--no-deps` 装两个本体包。
   但注意 **`onnxruntime` 和 `sox` 不能省** —— 代码里那个 25Hz 分词器分支在
   **导入时**就要它们，缺一个 `import qwen_tts` 直接失败（哪怕我们的 12Hz 路径
   根本不会调它）。`sox` 在 PyPI 上只有源码包，好在它本身是纯 Python，能装上。
4. **`transformers` 不许过 5.17。** 5.17.0 把 `rope_theta` 从 `MimiConfig` 上挪走了，
   加载权重时直接抛 `AttributeError`，快路（CUDA）与兜底路（CPU）会一起死。
   本文件所在的 `requirements-tts.txt` 里钉死 `transformers==5.15.1`。
   这个结论与 Python 版本无关：3.11 与 3.14 都测过，都在 5.17.0 失败、5.15.1 通过。

## 二、起服务 / 验证

**平时不用手动起。** 主程序在合成开工前会自动探活：没在线就用本服务的 `.venv`
把 `serve.py` 拉起来，整期（整批）跑完再停掉、把显存还回去；已经在跑的服务它一概不动。

**环境齐没齐是配置页的事，不是合成页的事。** 探活分三态——**环境没建** / **依赖没装齐** /
**模型没下**——对应的动作只有一个：回配置页点「搭建」。三态的措辞会逐条说清装到哪一步、
还差什么，不会用一句笼统的「还没装好」盖过去。三样都齐了，剩下的就只有「在不在线」，
而那一件事不需要用户做任何操作。

下面三条命令是单独调试用的：

```
.venv\Scripts\python.exe serve.py        :: 手工起服务（默认 127.0.0.1:9880，跑 Base）
.venv\Scripts\python.exe check.py        :: 验收：真合成一句，落成 wav
.venv\Scripts\python.exe make_voice.py --project-dir ..\projects\某项目
                                         :: 给某个项目录 / 查 / 继承角色音色档案
```

`serve.py` 与 `check.py` 都吃 `--model`（默认指向 Base）；`check.py` 走克隆时还要
`--ref` / `--ref-text`，缺了会被拒。

`check.py` **不会碰 LM Studio** —— 它只读看一眼你在跑什么，然后自己决定上 GPU 还是走 CPU。

**改了 `serve.py` 必须重启进程才生效**（模型懒加载，权重在第一个请求时才进显存）。
验收完记得把服务停掉，否则它占着显存，别的项目录参考音频时会退 CPU（见第五节）。

## 三、显存策略（本机最关键的一条）

这台机器同时跑着 LM Studio 的 35B。所以有两条硬规矩。

**一、服务绝不抢显存。** 加载前先读一次空闲显存，够才上 GPU：

| 空闲显存 | 行为 |
|---|---|
| ≥ 5300 MB | 上 GPU + CUDA 图 |
| < 5300 MB | 退 CPU（见下面第二条），并在日志与 `/health` 里说清还差多少 |

门槛拆开是：权重约 3.4 GB + 激活与 CUDA 图缓冲 1.1 GB + 安全余量 0.8 GB。

服务启动本身**不占显存**（模型懒加载，第一个请求才加载）。

**二、显存不足时退 `qwen-tts` 官方包走 CPU。** 退让分两级，都在代码里：

| 级 | 谁判 | 行为 |
|---|---|---|
| 1 | `pick_device()` | 空闲 < 5300 MB 即返回 `cpu`——四条分支：配置显式指定 / 读不到显存 / 强制 GPU 但不够 / 自动判定不够。人话原因写进日志与 `/health` |
| 2 | `Engine.ensure()` | 按序试 `faster-qwen3-tts` → `qwen-tts` 两个后端，前者抛错就换后者 |

第一级退回 `cpu` 之后，CUDA 图包接不住：它在源码里硬判设备必须以 `cuda` 开头
（`model.py`：`if not device.startswith("cuda"): raise ValueError("CUDA graphs require CUDA device")`），
**它自己没有 CPU 模式**。所以退到 CPU 时真正干活的是官方 `qwen-tts` 包——
`_load_official()` 按设备给 `device_map`（`cuda:0` 或 `cpu`）。

**代价是慢，不是不可用。** 官方包在 CPU 上实测可跑（`tools/probes/probe_cpu_vs_cuda.py
--path cpu`，float32）：同一句 CPU 13.9 秒 vs CUDA 图 1.1 秒，差 12.5 倍，RTF 8.7。

这条路能成立的前提是 `transformers` 钉死 5.15.1：5.17.0 把 `rope_theta` 从
`MimiConfig` 上挪走，加载权重直接抛 `AttributeError`，**快路与兜底路会一起死**。
所以 `requirements-tts.txt` 精确钉 `transformers==5.15.1`（是等号，不是区间）。
5.15.1 / 5.16.0 / 5.16.1 都能加载，首个坏版本是 5.17.0；与 Python 版本无关，
3.11.9 与 3.14.3 实测一致。

尽管兜底可用，正常路径仍然是**腾出显存走 GPU** —— CPU 慢 12.5 倍，只适合应急，
而主程序已经把「腾显存」这一步做进合成流程了。

### 实测（RTX 4060 Laptop 8GB，1.7B）

| 项目 | 数值 |
|---|---|
| 权重加载 | 11.3 秒 |
| 首句总耗时 | 17.7 秒（含加载） |
| 音频时长 | 10.32 秒（52 字） |
| 净合成速度 | 约 6.4 秒 / 10.32 秒 ≈ **1.6× 实时**（比实时快） |
| 显存占用 | 5064 MB |

## 四、接口

### `POST /tts` —— 本项目既有形状（主程序接入零改动）

```json
{ "text": "要念的正文", "voice": "Serena", "speed": 1.0,
  "instruct": "可选，自然语言语气指令", "emotion": "可选，折成 instruct",
  "degree": "可选，情绪档位：none 整句不发情绪指令，light 拼「用略带X的语气说」",
  "ref_audio": "可选，参考音频路径（给了就走音色克隆）",
  "ref_text":  "走克隆时必给，那段音频的转录文本" }
```

返回 `audio/wav` 字节（16-bit 单声道 PCM）。

`ref_audio` / `ref_text` 是 Base 变体接入后新增的两个字段，服务**按有没有
`ref_audio` 显式分流**：有就走参考音频克隆（ICL，`xvec_only=False`），没有才走
内置音色表。两条路分开写，不靠「挨个方法试一遍」去猜 —— 那种写法在 Base 上会抛
`ValueError` 而不是 `TypeError`，兜不住，报错还完全指不到病根。

两个字段都要在前置校验里过：路径不存在 → 400；走了克隆却没给 `ref_text` → 400
（ICL 拿它当参考音频的「台词」，缺了它参考内容会串进结果）。给了 `ref_audio` 时，
种子由**音频内容指纹**派生而不是 `voice` 那个名字，见第五节。

### `POST /v1/audio/speech` —— OpenAI 标准形状（换引擎即插即用）

```json
{ "input": "要念的正文", "voice": "Serena", "response_format": "wav" }
```

### `GET /health` / `GET /speakers`

健康检查（设备、后端、空闲显存、加载耗时、**`model_kind`**）与音色清单。

`model_kind` 告诉调用方此刻加载的是哪个变体（`base` / `custom_voice`），界面据此
决定「音色」那一栏长什么样。`/speakers` 在 Base 下把两个字段分开报：`speakers`
如实报空（此刻能直接用来合成的音色一个都没有），`builtin` 给出那九个内置音色名
（录参考音频时挑一个），另带 `need_reference: true`。

## 五、音色、语气与稳定性

### 音色来自一段参考音频，不来自模型

`serve.py` 跑的是 **Base** 变体，它**没有内置音色** —— 音色由一段 5～8 秒的参考
音频决定。这段音频是**项目资产**，落在项目的 `音色/<角色>/` 下，由 `make_voice.py`
一次性录好：

```
音色/A/ref.wav        参考音频（整期音色的源头）
音色/A/ref.txt        转录文本（ICL 必给，缺了它请求被 400 挡下）
音色/A/profile.json   溯源：内置音色名 · 录制设备 · 种子 · 内容指纹 · 参考文案
```

A、B 各一份，整期所有句子读的都是它。换项目互不影响；要与别的项目一致，用
`--from` 把那份目录整个复制过来 —— 复制的是文件，逐字节相同，不靠重新生成碰运气。

**为什么不是「内置音色」那条路**：同一个句子换一次种子，内置音色变体的 F0 相对
极差是 46.9%（A 角）/ 35.8%（B 角），Base + ICL 是 22.5% / 13.1% —— 音色锚在参考
音频上，句间漂移小一半以上（实测 24 句，逐句数值见 CHANGELOG）。
代价是每个项目多一步录音，约半分钟，只录一次。

**克隆固定走 ICL**（`xvec_only=False`）：参考音频连同它的转录文本一起进上下文，
相当于跟模型说「你听一遍这个人怎么说话，再照这个念」。只喂向量的 `xvec_only=True`
官方标为实验性，而且漂移更大（27.4% vs 13.1%），所以不进产品。

### 录参考音频时能挑的内置音色

Base 下 `/speakers` 的 `speakers` 如实报空（此刻一个能直接用来合成的音色都没有），
另用 `builtin` 字段给出 CustomVoice 那九个 —— 它们是**录参考音频时的基准**：

| 内置音色 | 性别 | 母语 |
|---|---|---|
| Serena | 女 | 普通话 · 温暖柔和 |
| Vivian | 女 | 普通话 · 明亮略锋利 |
| Uncle_Fu | 男 | 普通话 · 低沉醇厚 |
| Dylan | 男 | 普通话 · 北京话 |
| Eric | 男 | 普通话 · 四川/成都话 |
| Ryan | 男 | 英语 |
| Aiden | 男 | 英语 · 美式 |
| Ono_Anna | 女 | 日语 |
| Sohee | 女 | 韩语 |

两个字段分开报，界面就不会把「录参考音频用」误当成「合成可用」。
**双人对谈建议**：A 角 = `Serena`（温润女声），B 角 = `Uncle_Fu`（低沉男声）
—— 这也是出厂默认值；两个都是女声或都是男声时，双人对谈不易分辨。

参考文案是脚本里的**固定常量**（`REF_TEXTS` 那两句），不随项目内容变 —— 拿当期
台词当参考会让「换个项目音色就变」；要跨项目一致，源头必须与项目无关。

### 参考音频的确定性边界（一个真踩过的坑）

同设备、同后端下，同一套内置音色名 + 同一句参考文案，录出的音频**跨进程逐字节
相同**（实测同一目录 `--force` 重建三次，sha256 全同；换项目也一样）。

**但前提不能省。** `pick_device()` 在空闲显存不足时是**静默**退 CPU 的，而 CPU 与
GPU 出的是两条不同的波形 —— 实测同一套输入：GPU 得 `sha256[:16]=713bab2d382ab0fd`
/ F0 228.6 Hz / 5.44 s，CPU 得另一条 / F0 250.0 Hz / 5.52 s。踩法很隐蔽：上一期
已把服务拉起来占住显存，新项目录档案就悄悄落到 CPU 上，慢十几倍，音色也不再与
别的项目对齐，而事后完全查不出原因。

所以 `profile.json` 里记了 `device` 与 `backend`（`make_voice.py --list` 会打出来），
退 CPU 时工具与主程序日志都会**点名**，不会只当普通日志混过去。真要跨项目强一致、
又不依赖设备，用 `--from` 继承。

### 语气

**语气**：`instruct` 吃自然语言（如「用好奇的语气说」），主程序脚本行里的 `emotion`
字段就是它的来源。但只有**真情绪**才转——标签里另有 9 个是语篇功能（开场 / 过渡 /
总结 / 解释 / 比喻 …），说的是这句话在结构上干什么，跟心情无关，拼成「用过渡的语气
说」对模型是纯噪音。真情绪那 7 个（平静 / 好奇 / 疑惑 / 恍然 / 肯定 / 感慨 / 轻松）
与主程序 `EMOTION_VOCAB` 同源，有测试盯着两处不许走散。

**档位**：`degree` 由主程序按素材类型的范式卡给（`emotion_level`，两档 `none`/`light`），
它管两件事。

`none`（不写心情的文体，卡上不写、写错也落这一档）**整句不发情绪指令**。这一档的稿子里
仍会出现真情绪词——主程序那边 `emotion` 是必填，词表里又恰好没有表示「无」的合法值，于是
拿「平静」当「不加修饰」的代码字在用。上游 `paradigms` 明写这一档「不贴语气指令」，拦在
`build_instruct()` 这一跳才等于文档说的行为；不拦就会发出「用平静的语气说」。语篇标签
本来就不转，同一条分支一并覆盖。

`light` 时措辞加一个「略带」（「用略带感慨的语气说」）——实测这一档能把句与句之间的
起伏收窄，而「明显 / 非常」方向会反转（同一个词在肯定句上抬高起伏、在中性句上又压低），
所以服务端只认这一档；别的值（含不传）只按「不加『略带』」处理，不静默当成「略」。
措辞表只在本文件对应的 `build_instruct()` 一处，主程序给的是档位名、不是句子。

语速不归档位管：`speed` 只由请求体决定（主程序送的是恒 1.0，变速在它本地用 atempo 做），
所以 `none` 档若收到非 1.0 的语速，仍会拼出语速那一句。

**同一句话，永远是同一条波形。** 种子按 `(文本, 音色标识)` 派生（`sha256` 前四字节），
逐句记进日志。音色标识走克隆时**不是**音色名，而是参考音频的**内容指纹**
（`sha256` 前 16 位）—— 用名字的话，同一份音频复制到新项目就换了种子、波形跟着全变，
而「换个项目音色照旧」正是这套档案要保证的事。听到某一句不对劲，照原样重跑得到的
就是同一条，不必靠重跑碰运气。

**温度 0.4**（库默认 0.9）。压低是为了收窄采样分布、减少音色的逐句漂移。没有再往
下压到 0.2 —— 实测那一档 20 个种子里有 4 句跑满生成上限、炸成两分半噪声，而 0.4 与
0.9 都是 0/20。

**生成失控有三道兜底**：按字数给生成帧数上限（8 帧/字，短句 120 帧兜底）；顶到上限
九成五即判为失控，依次换种子、去掉语气各试一次；三试都炸就如实报错，不返回一段噪声。
（模型偶尔落进重复循环，一路念到上限才停；种子是内容派生的，坏种子会稳定复现，所以
这里不是原样重试，而是换一条随机路径。）

**服务刚起来时还会跑一次哑合成**（引擎加载完成后、接受请求之前）。CUDA 图捕获之后
首次 replay 的状态与之后不一致，实测表现为「第一个请求与同参数的第二个请求音频
不同」；预热把这个差异消耗掉，「同一句永远同一条」对第一个请求也成立。

## 六、与主程序对接

引擎键是 **`qwen3tts`**。主程序侧的相关配置：

| 配置项 | 默认值 | 说明 |
|---|---|---|
| `tts.engine` | `qwen3tts` | 切到本服务；`edge` 仍可选 |
| `tts.qwen3tts_host` / `_port` | `127.0.0.1` / `9880` | 本服务地址 |
| `tts.qwen3tts_voice_a` / `_b` | `Serena` / `Uncle_Fu` | **录参考音频时挑的内置音色**，不是合成音色。取值来自 `/speakers` 的 `builtin`，界面上是下拉 |
| `tts.unload_llm_before_synth` | 开 | **合成前自动腾显存**，见下 |

`_voice_a` / `_b` 这两个键的语义随 Base 接入变了：合成用的音色已经由项目那份参考
音频决定，这两个名字现在只在**录参考音频**那一步起作用 —— 改它会得到另一段参考
音频，从而换掉整期音色，但不会「只换这一句」。界面在 Base 下把那一栏的文案改成
「录参考音频用的内置音色」，正是这个原因。

名字由服务端枚举（`/speakers`），主程序不写死任何音色表；服务没起来时下拉会明确
报错，不会拿一份假清单顶包。`make_voice.py` 直接跑命令行时有一份自己的默认值，
它与上表的出厂默认**必须一致** —— 两边不一致会让两个入口录出两套音色，有测试逐条
比对。

**合成前腾显存**：`tts_engine.synthesize()` 开工前会把 LM Studio / Ollama 里驻留的
模型请下显存（`lms unload --all` / `ollama stop`）——语音合成全程用不到语言模型，
而它们一占就是十几 GB，两者同时在场必然抢显存。关掉这个开关则完全不碰，
机器资源充足、想一边跑 LLM 一边合成的，关掉即可。

**流程一行不改**：本服务一次返回一句一个 wav，与逐句循环的现有形状完全一致，
字幕时间轴与逐句时长标定链路免改（仅需重跑几期让标定收敛到新引擎）。

## 七、目录

```
tts_service/
  setup_env.py               唯一一份安装实现：建环境 → 装依赖 → 下两个模型 → 自检
  setup.bat                  薄壳：找机器上的 Python，然后调 setup_env.py
  requirements-torch.txt     torch/torchaudio，自带 pytorch 源
  requirements-tts.txt       其余依赖，自带 PyPI 源
  .venv/                     本服务自己的环境（由程序建，不入库）
  serve.py                   薄服务本体（HTTP + 引擎 + 显存策略）；跑 Base 变体
  make_voice.py              角色音色档案：生成 / 继承 / 查账（跑 CustomVoice，
                             一次性进程，跑完就退）
  check.py                   验收脚本（不碰 LM Studio）
  fetch_model.py             模型下载（三源自动切换，断点续传，两个模型一起下）
  models/                    权重（Base + CustomVoice 各一份，见第一节）
```

`make_voice.py` 是三个动作共用的入口，主程序在合成前缺档案时会自动调它：

| 动作 | 命令 | 用途 |
|---|---|---|
| 生成 | `--project-dir <项目>` | 缺谁录谁，已有就跳过。主程序走这条 |
| 继承 | `--project-dir <新> --from <老>` | 整目录复制，跨项目音色一致走这条 |
| 查账 | `--project-dir <项目> --list` | 打印内容指纹、录制设备、内置音色名、参考文案 |

`--list` 的「录制设备」一栏是排查两份档案音色不一致的第一线索，见第五节。

解释器在 **`.venv/`**：本服务自己的一份，版本由建环境时那台机器上的 Python 决定。
主程序不用它，它也不进主程序的依赖。

**MIT 与 Apache-2.0 都是宽松许可，整条链路没有非商业条款**：商用不需要额外授权、

**真正要留意的不在许可，在两处合规：**

- **音色来源。** 本服务跑 Base 变体，音色来自项目自己那份参考音频，而那份音频是
  `make_voice.py` **用 CustomVoice 的九个预设音色合成的**（不是真人录音），所以
  走完整条链路出来的声音不涉及他人声音权 —— 这九个是模型自带的合成音色。
  **别拿一份真人录音去当参考音频**：那才会落进克隆真人声音的场景，受《民法典》
  第 1023 条声音权保护，未经许可商用属于侵权。这条与模型许可无关，许可再宽也不覆盖。
- **生成内容标识。** 商用发布 AI 生成音频，需按《人工智能生成合成内容标识办法》
  （2025 年 9 月 1 日施行）加标识，显式或隐式。

作为对照，备选的 **edge-tts** 是 **LGPL-3.0**（仅指那个 Python 客户端库）；它并不
在本地发声——声音来自**微软 Edge 浏览器的在线朗读接口**，那不是微软公开授权、
发放凭据的 API，而是浏览器自用通道，条款与可用性由微软单方面决定，产出的音频同样
受微软服务条款约束。两条路的差别在这里，不在「本地还是云端」。
